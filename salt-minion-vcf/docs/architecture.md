# Architecture

## One image, multiple deployment targets

```text
                         +------------------+
                         | Any Salt-aware   |
                         | client           |
                         | (CLI, RaaS, CI/  |
                         | CD, custom, ...) |
                         +---------+--------+
                                   |
                                   v
                         +------------------+
                         | RaaS / Salt      |
                         | Master           |
                         +---------+--------+
                                   |
                 Salt job targeted by Minion ID
                                   |
                   +---------------+----------------+
                   |                                |
                   v                                v
        +----------------------+        +----------------------+
        | Docker / Compose     |        | Kubernetes           |
        |                      |        |                      |
        | salt-minion-vcf      |        | StatefulSet/Pod      |
        | container            |        | same container image |
        +----------+-----------+        +----------+-----------+
                   |                               |
                   +---------------+---------------+
                                   |
                            configured Salt extensions (for example saltext-vcf)
                                   |
               +-------------------+------------------+
               |                   |                  |
               v                   v                  v
            vCenter               NSX              SDDC-M / Ops
```

The top of the diagram is deliberately generic: the Minion only ever sees Salt
jobs dispatched from a Master, so any client capable of talking to Salt (the
Salt Config CLI, a RaaS UI/API, a CI/CD pipeline, custom orchestration) works
identically. Nothing here is coupled to a specific dispatching tool.

The artifact boundary is the Docker image. Docker Compose, raw Kubernetes YAML,
Helm, and the future OVF/OVA are deployment wrappers around that same artifact.

## Kubernetes identity

Default Kubernetes mode uses StatefulSet.

Each Pod has:

```text
<release>-salt-minion-vcf-0
<release>-salt-minion-vcf-1
...
```

The Pod name becomes the Minion ID and the Pod owns a dedicated PVC containing:

```text
/etc/salt/pki/minion
```

This prevents key/identity loss across Pod recreation.

## Configuration model

Docker:

```text
Environment variables -> entrypoint -> 10-master.conf
```

Kubernetes:

```text
Helm values
    |
    v
ConfigMap
    |
    v
/etc/salt/minion.d/10-master.conf
```

Dynamic identity remains runtime-generated by the container.

## No inbound application Service

A Salt Minion initiates its connections toward the Master. The headless
Kubernetes Service is present only for StatefulSet identity; it is not a Salt
traffic load balancer.


## Extension packaging

The container is intentionally extension-agnostic.

```text
salt-extensions.txt
    |
    +-- saltext.vcf[all]
    +-- another Salt extension
    +-- customer/community extension
    |
    v
salt-pip install -r
    |
    v
versioned immutable image
```

Docker, Kubernetes, Helm, and the future OVF all consume the same built image.
